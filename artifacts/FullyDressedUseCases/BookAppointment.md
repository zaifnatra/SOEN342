# Fully Dressed Use Case: Book Appointment

| Field | Description |
|---|---|
| **ID** | UC-2 |
| **Title** | Book Appointment |
| **Description** | A patient or administrative staff member requests an appointment. The system checks access, availability, scheduling constraints, and any required referral. If the checks pass, the system creates and automatically confirms the appointment. |
| **Primary Actor** | Patient or Administrative Staff acting on behalf of a patient. |
| **Stakeholders and Interests** | **Patient:** Wants a confirmed appointment for the requested service.<br>**Administrative Staff:** Wants appointments booked with the correct patient and appointment details.<br>**Healthcare Professional:** Wants appointments to respect their availability and avoid scheduling conflicts. |
| **Pre-Conditions** | The requester's identity and role are already known to the system (assumption). |
| **Post-Conditions** | **Success:** An appointment is created for the patient, healthcare professional, clinic location, service, and requested date/time. Its status is set to `confirmed`, and the system returns a confirmation.<br><br>**Failure:** No appointment is created. The system returns an error explaining why the request was rejected. |
| **Inputs** | 1. `patientID` (Identifier)<br>2. `professionalID` (Identifier)<br>3. `clinicLocationID` (Identifier)<br>4. `serviceType` (Requested service)<br>5. `requestedDateTime` (Date and time)<br>6. `referralID` (Identifier, if required) |
| **Outputs** | **Success:** `confirmation(appointmentID, requestedDateTime, "confirmed")`.<br><br>**Failure:** `errorMessage(reason)`. |
| **Main Success Scenario** | 1. The requester submits the booking details using `bookAppointment(patientID, professionalID, clinicLocationID, serviceType, requestedDateTime, referralID)`.<br>2. The system checks that the patient exists and the requester is authorized to book for that patient.<br>3. The system checks the professional's availability at the requested clinic and the applicable scheduling constraints, including conflicts across clinic locations.<br>4. If the service requires a referral, the system checks that a referral is supplied and valid for the request.<br>5. The system creates the appointment with the submitted details and automatically sets its status to `confirmed`.<br>6. The system returns the appointment ID, requested date/time, and confirmed status. |
| **Extensions (Alternative / Failure Scenarios)** | **2a. Patient not found:**<br>1. The system returns an error. No appointment is created.<br>2. The requester corrects the patient ID and retries from Step 1, or stops.<br><br>**2b. Requester is not authorized:**<br>1. The system returns an access denied error. No appointment is created.<br>2. The use case ends.<br><br>**3a. Professional unavailable or scheduling constraint not met:**<br>1. The system returns an error explaining the scheduling problem. No appointment is created.<br>2. The requester changes the booking details and retries from Step 1, or stops.<br><br>**4a. Required referral missing or invalid:**<br>1. The system returns an error explaining the referral problem. No appointment is created.<br>2. The requester supplies an appropriate referral and retries from Step 1, or stops. |
| **Special Requirements** | 1. Access to patient and appointment information is restricted according to the requester's role.<br>2. Relevant booking activity is recorded for accountability and confidentiality. |
| **Technology and Data Variations List** | `referralID` may be omitted when the requested service does not require a referral. |
| **Open Issues** | 1. Which services require a referral, and what rules determine whether a referral is valid?<br>2. What additional scheduling constraints apply to each service? |
